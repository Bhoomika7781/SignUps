How one iteration works

            

              
    
                
  1. Start kvdb serve as a child process.
    2. 
                
  2. Two (or more) writers send random put, del and batch ops at the same time. Some modes add a reader or a compactor.
    3. 
                
  3. The tool writes down every op it sent and every ACK it got back. That list is the oracle. It never trusts the database.
    4. 
                
  4. After a random number of ms it kills serve with SIGKILL (TerminateProcess on Windows), usually in the middle of a write.
    5. 
                
  5. It runs kvdb open (recovery), kvdb check and kvdb dump.
    6. 
                
  6. It compares the dump with the oracle:
                  every ACKed write must be there (unless a later ACKed write replaced it), in-flight writes may be there or not,
                  a batch is all or nothing, and every value must be complete and belong to its key.
    7. 
                
  7. Any mismatch stops the run and prints what was expected and what was found.
    8. 
              

            

          

          

            
What the columns mean

            

              
kill@when the kill happened, ms after serve was ready

              
sentwrite ops sent in this iteration

              
ackedops that got ACK, so they must survive

              
in-flightsent, no answer before the kill. Either outcome is legal.

              
fullrejected by max_bytes. Must NOT appear.

              
tornbytes of half-written record that open cut off

              
recoverytime open took to rebuild the index
